## Stage 0: Orientation (done, docs only, no code)

**Understanding.** Zuscar is a single-venue, online-first hospitality system (restaurant, bar/club, ~13 rooms) built as a modular monolith: Next.js on Vercel proxies `/api/*` (ADR-05) to a Go/Gin API on Render, which is the only client of Supabase PostgreSQL (ADR-02). ## Stage 10b-2 (backend): Idempotency-Key
- **Built:** migration `0011_idempotency.sql` (`idempotency_records`); package `internal/platform/idempotency` (middleware `Required` and `Optional`, `Begin`, `Complete`, `Purge`); `send-to-kitchen` now requires the `Idempotency-Key` header and `POST /orders` accepts it. `openapi.yaml` updated (header, 400, 409 `idempotency_conflict`, 422 `idempotency_key_reused`); `routes.csv` unchanged.
- **How it works (S-46):** the service claims the key as the first step of its own transaction and stores the response as the last, so the stored response and the work commit together or not at all. A duplicate at the same moment waits for the first and then replays it; the replay carries `Idempotent-Replayed: true` and uses no ticket or order number. Same key with a different request or user is 422. A failed request rolls back, so its key stays free for a corrected retry. Stage 11 reuses `Begin` and `Complete` for finalisation and payments.
- **Held by the database:** a key is kept at least 24 hours whatever the setting says (CHECK); a completed record cannot be edited; the table cannot be truncated; the key is unique per endpoint.
- **Ran (real PostgreSQL 16 in the authoring sandbox):** four new tests: replay, key reuse by another order, body and user, failed request frees its key, six simultaneous identical sends give one ticket; `POST /orders` with and without a key; retention (24 hours by default, the setting lengthens it, a setting of 1 hour is held at 24, the table refuses less) and `Purge` removing only expired records; a held key answers 409 after the wait and works once released.
- **Not in 10b-2:** the cleanup job is not scheduled; `idempotency.Purge` exists and returns the number removed, and the deployment stage must call it on a schedule (until then expired rows only take space, and an expired key is treated as new when it is used again). The existing 10b-1 and 10a tests were updated to send a fresh key per send.
- **You must run a migration:** `docker compose run --rm backend /app/migrate up` (0011). Frontend: when the POS screens call send-to-kitchen they must send one `Idempotency-Key` per tap intent; nothing in the frontend repo calls it yet.
